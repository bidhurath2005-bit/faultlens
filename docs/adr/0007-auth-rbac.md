# ADR-007: Authentication and role-based authorization

- **Status:** Accepted
- **Date:** 2026-11-19

## Context
Three roles (Admin, SRE Engineer, Viewer) need backend-enforced permissions. Fault injection and settings are
dangerous operations. The SPA must not keep long-lived secrets in JavaScript-readable storage.

## Decision
- Passwords are hashed with **argon2id** (`argon2-cffi`, per-hash salt). Logins for unknown users still run a
  hash, so there is no user-enumeration timing oracle.
- **Access token**: HS256 JWT, 15 min, claims `sub/usr/role/typ/iat/nbf/exp/jti/iss`, held in memory by the SPA.
- **Refresh token**: 256-bit random value stored only as SHA-256, sent as an
  `HttpOnly; SameSite=Strict; Path=/api/v1/auth` cookie and **rotated on every use**. Re-use of a rotated token
  revokes the whole token family. Logout, password change, role change and deactivation also revoke sessions.
- Every request re-loads the user record, so deactivation or a role change invalidates existing access tokens immediately.
- Roles map to permissions in one place; every protected route declares `Depends(require(Permission.X))`.
  Unknown roles are denied.
- WebSockets authenticate with the access token in the first frame (never the URL) and enforce `Origin`.
- The first admin comes from the environment (`BOOTSTRAP_ADMIN_PASSWORD`, generated by the setup script) and is
  created only when no users exist.

## Alternatives considered
- Server-side sessions only: simpler revocation, but needs a session-store lookup per request and CSRF tokens for every write.
- External IdP (Keycloak/OIDC): better for production, too heavy for a self-contained demo.
- Tokens in localStorage: exfiltratable via XSS; rejected.

## Consequences
- 15-minute access tokens bound the damage of a leaked token; refresh is transparent to users.
- HS256 uses one shared secret: fine for a single backend, but asymmetric keys would be needed for third-party verification.
- No MFA and no account lockout beyond rate limiting; documented in SECURITY.md.
